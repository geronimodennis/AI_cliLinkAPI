# Architecture and provider integration

`server.ts` owns HTTP authentication order, bounded bodies, OpenAI-shaped errors, SSE/backpressure and disconnect/timeout signals. `config.ts` owns strict runtime validation and directory authorization. `sessions.ts` locks workspace execution within one aiclitoaiapi process; new requests are isolated; `tool-sessions.ts` retains bounded, expiring one-use Codex continuations for external tool results and reserves their workspace. `remote-agents.ts` brokers bounded, expiring tool tasks to authenticated outbound workers, while `remote-worker.ts` owns the persistent remote workspace and built-in/custom tool execution. `permissions.ts` owns secret-file permissions. `sandbox.ts` owns native profiles and preflight probes. `chat-compatibility.ts` validates and normalizes the OpenAI request envelope before model discovery or streaming. `requests.ts` retains conversation/tool-history validation and message/reasoning translation. Providers are registered in `providers/registry.ts` behind `providers/types.ts`.

Remote operation deliberately separates three kinds of state: clients carry conversation history in every request; the worker's filesystem and Git checkout persist across requests and restarts; and gateway task correlation exists only in bounded process memory until completion, cancellation, timeout, or restart. A worker long-polls outbound, executes a delivered task once, and retries only delivery of the captured result. The original chat request resumes its selected provider after that result is appended as a tool turn.

When a request registers client functions, `server.ts` adds instructions to use the client's list, search, read, or shell function to inspect its current workspace before coding or reviewing. With `X-Remote-Agent-ID`, it also supplies `remote_*` tools and instructions to discover the connected remote workspace. These are model instructions, not a gateway filesystem scan or a guarantee that the model will call a tool. Client functions return OpenAI `tool_calls` for the API client to execute; a single remote tool call is sent through the worker broker, then its result is appended to the request and generation continues. Provider-native file and shell tools run on the gateway computer.

The registry combines the Codex adapter with configured Antigravity CLI providers, discovers their models, and routes generation by public model ID. Codex owns login verification, catalog pagination/filtering, thread creation, native reasoning configuration, final-answer extraction, cancellation and normalized errors. It uses a dedicated stdio app-server for discovery and generation, retaining a connection only while a bounded external tool continuation is pending. No app-server TCP listener is exposed. Antigravity uses the official `agy` CLI for model discovery and stream-json generation; its JSON-schema bridge produces one external function call or a final answer. Request IDs correlate safe structured logs; normal logs omit prompts, responses, headers, account identity and raw upstream stderr. Metadata and generation are bounded separately. Slow consumers are subject to the request deadline; RPC event count, line size and final delta accumulation are bounded. No automatic aiclitoaiapi retries occur.

The official SDK was inspected first. Version 0.155.0 exposes `Thread.run`, `runStreamed`, AbortSignal and sandbox modes. Its typed thread options do not provide permission-profile selection/model discovery, and its `agent_message` events omit final-versus-commentary phase metadata. Current app-server provides `model/list`, incremental `item/agentMessage/delta`, phase-labelled items, and experimental named permission profiles. Therefore this release uses the official app-server instead of the SDK for execution and metadata. The CLI is used for official login and sandbox diagnostics only. The SDK remains pinned for comparison/migration; there is no fake SDK backend.

Protocol fields were checked against `codex app-server generate-ts --experimental` from the pinned installed binary. In particular, its legacy `SandboxPolicy` lacks the `ReadOnlyAccess` field shown in newer online documentation, so the implementation uses `permissions: "aiclitoaiapi"` on threads and `permissionProfile: "aiclitoaiapi"` on standalone probes. It verifies the returned active profile and never passes a legacy `sandbox` override that could supersede the profile. Permission-profile APIs are experimental; reject incompatible versions and re-run platform checks before upgrades.

To add a provider, implement `Provider.models`, `generate`, `close`, and capability flags. `generate` accepts AbortSignal and supplies usage only when the backend reports it. Document how streaming works for that provider: Codex emits only real final-answer deltas and rejects buffered-only streaming, while Antigravity's JSON-schema tool bridge emits a buffered final value as one delta. Normalize errors without forwarding sensitive backend messages. Own authentication and provider sessions inside the adapter. Add explicit config discrimination and registry selection, validate native reasoning against discovery, and add adapter/protocol and live tests. Do not assume another CLI's authentication, role mapping, sandbox controls or reasoning levels match Codex or Antigravity.
